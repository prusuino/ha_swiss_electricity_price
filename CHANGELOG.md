# Changelog

## 1.4.1 — 2026-10-26

- Fixed: a tariff file holding more than one year's tariffs — operators commonly append next year's set to this year's, under the same product names — was parsed as one. Whichever year happened to come last in the file won for each product, municipality and metering fee, and the validity-year diagnostic reported the first set's year (2027 for BKW's file, whose 2027 tariffs precede the 2026 ones). Only the records valid today are used now, in the setup dialog's product and municipality lists as well as for every sensor. When the current period ends (New Year, typically), the file is re-read right then instead of at the next 24-hour fetch. A file with no record valid today falls back to the nearest upcoming set, or failing that the most recent one, with a warning in the log. (#1)
- Fixed: an operator whose registered link redirects straight to the tariff file instead of showing a web page (BKW's `www.bkw.ch/de/tarife-json`) could not be set up without pasting the file's URL by hand — the auto-detection only looked for a link to a `.json` file in the page and did not notice that the page *was* the file. The final URL of such a redirect is used directly now. (#1)
- Fixed: a municipality levy that applies to secondary meters only ("Konzessionsabgabe für Zweitzähler", listed by BKW next to the regular concession fee of the same municipality, usually at a lower rate) replaced the regular levy, because both carry the same municipality name and the secondary-meter one comes later in the file. Such records are recognised by their name or comment (German, French, Italian, English) and no longer override the regular levy; a municipality that has nothing but a secondary-meter levy keeps it. Reported, together with a proposed fix, by @DerAutomatiker in #2.
- Fixed: two products whose names differ only in characters that are dropped from entity ids — BKW's grid products "Benutzungsdauer <= 3500h/a" and "... > 3500h/a" — collapsed into one id, and Home Assistant refused the second entity ("does not generate unique IDs"). The later of two such names now gets a short code appended to its id; the first keeps the plain id, so existing entities are unaffected.
- When the link an operator registered with ElCom for the current year is unusable, the link registered for next year is tried before giving up — from autumn on, many operators have already reported next year's (often newer) link, and that file usually holds the current year's tariffs as well. Applies to setup and to every daily update; a manual URL override is never second-guessed this way.
- Nothing to do after updating: no re-configuration, no changes to existing entities.

## 1.4.0 — 2026-08-29

- Fixed: the high/low tariff switch was only evaluated at the moment the tariff file was fetched, once every 24 hours. Whatever tariff level applied at that moment stayed on for the rest of the day — the tariff-level sensor, every product sensor and the combined current price could show the high tariff straight through a low-tariff night (and vice versa). The active time window is now resolved against the clock every time a sensor is read, and the sensors are refreshed at the minute a window starts or ends (e.g. 22:00 and 06:00), without any additional network traffic. The 24-hour fetch of the tariff file itself is unchanged.
- Changed: the entity ids suggested for newly created entities now carry a short per-entry code after the operator name, and product sensors carry their category (`sensor.elcom_<operator>_<id>_energy_<product>`, `sensor.elcom_<operator>_<id>_price_current`, `number.elcom_<operator>_<id>_vat_percent`, see the README table). Two entries for the same operator no longer collide into `_2` ids, and an energy, grid and metering product sharing one name no longer collide within a single entry. The manual base-fee sensor is suggested as `..._base_fee` instead of `..._grundgebuehr`. **Existing entities keep the ids they already have** — a suggested id only applies when an entity is first created — so nothing changes for automations, dashboards or statistics.
- Products, metering fees and municipalities that appear in the operator's tariff file after setup (a product added for next year) are now created automatically at the next update instead of needing a reload. Entities whose product has disappeared from the file report `unavailable` instead of `unknown`, as the README always promised; they are kept rather than deleted, so renames and customizations survive a file that is only temporarily incomplete.
- Manual entries: the "working tariff file found" repair notification is withdrawn again when the operator's link stops working, or when the entry is reloaded or removed, instead of lingering forever. The daily link check no longer delays startup, so a manual entry's entities come up immediately even when the operator's host is slow to answer.
- Setup dialog: only the operators actually shown in the picker whose registered link points at a `.json` file (at most 60 per search) have their tariff-file link verified, instead of every such operator in ElCom's directory being contacted the moment the dialog opens. The first form appears faster, and servers of operators you did not search for are no longer contacted.
- Setup dialog: adding an operator/municipality/product combination (or a manual entry for an operator) that already exists now shows a translated message instead of the raw text "already_configured". The message shown when ElCom's directory comes back empty now says so, instead of talking about a not-yet-chosen operator.
- The national-levies and VAT number entities update immediately when changed, including from the Configure dialog.
- Metering-fee and manual base-fee sensors show their unit as `CHF/month` instead of the abbreviation `CHF/M`.
- Documentation: the README entity table now lists the manual-mode entities and describes the diagnostics validity-year sensor as it actually works — the year comes from the tariff data's own `startDate`, and only a file without one falls back to a year in the file name (the 1.2.0 note below described the fallback only). SECURITY.md lists every endpoint the integration talks to and why operator links may be plain `http://`.
- Internal: both coordinators are bound to their config entry explicitly (avoids a deprecation notice on recent Home Assistant versions), the device is registered with the proper service entry type, and coordinators are named per entry so log lines can be attributed when several operators are configured.
- Nothing to do after updating: no re-configuration, no changes to existing entities.

## 1.3.1 — 2026-08-29

- Fixed: an entry could end up permanently broken when the operator's tariff-file host was unreachable at startup. 1.3.0 set the number entities up before the first data fetch; when that fetch failed, Home Assistant retried the entry without unloading the platform it had already set up, and the retry aborted with "config entry has already been set up!". That turns a temporary network problem into a terminal setup error, which stops retrying altogether and needs a manual reload. All platforms are now set up once, after the first fetch has succeeded. The number entities may briefly show "unavailable" during such an outage — the trade-off 1.3.0 tried to avoid, but the entry now recovers on its own.
- Fixed: a malformed tariff file from an operator (a price or time window missing a field, an unexpected structure) raised an unhandled error and was reported as an unexpected failure. Such files are now reported like any other data problem, leaving the entities unavailable until the operator publishes a usable file again.
- Added an English translation file. Without it, English — the default language — fell back to raw translation keys throughout setup, the options dialog and repair notifications.
- The minimum supported Home Assistant version is now declared correctly as 2024.12.0. The options dialog (national levies / VAT) has always required it, and entry migration required 2024.3.0, but hacs.json still claimed 2024.1.0.
- Corrected the municipality levy sensor's description, which named the wrong unit.

## 1.3.0 — 2026-07-17

- Setup now asks for your energy tariff product and grid tariff product separately, picked directly from the operator's own product names, instead of inferring the grid product from a single "customer tariff" selection. The previous naming-convention guess (energy product name + " Netz") does not reliably hold across operators — verified against real operator data, where the two products carry the same customer category but neither the same name nor a matching category label. Existing entries are migrated automatically, reproducing the same guess they already relied on, so already-working setups keep working unchanged.
- Fixed: a config entry's national-levies and VAT number entities (and, by extension, every other entity of that instance) could get stuck showing "unavailable" after a Home Assistant restart if the operator's tariff-file host happened to be briefly unreachable at boot — the whole entry's setup was gated on that first network fetch succeeding, even for the two number entities that only ever read local config values and never needed the network at all. They're now set up independently of it.
- Fixed: adjusting the national-levies or VAT number briefly dropped every entity of that instance to "unavailable" and re-fetched the operator's tariff file over the network, just to make the combined-price sensors pick up the new rate. They now update immediately from already-fetched data instead.

## 1.2.0 — 2026-07-17

- Five new diagnostic sensors per operator instance (`sensor.elcom_<operator>_diagnostics_host` / `_path` / `_filename` / `_year` / `_last_checked`) showing which tariff-file source is currently in use: the resolved tariff-file's host, directory path, and file name (split apart so no single value is too long to fit the diagnostics card; the full URL and the ElCom-registered URL are available as attributes on the host sensor), the year found in the filename, and the timestamp of the last successful check — useful for spotting a stale or misdetected link without digging through the logs. Not shown for fully manual rate entries, which have no tariff file to report on.
- Setting up the same operator + municipality + customer-tariff combination (or the same operator twice in manual mode) a second time is now rejected instead of silently creating a duplicate entry.

## 1.1.0 — 2026-07-17

Initial public release.

- Nationwide Swiss coverage: works with any grid operator registered with ElCom, not just a single utility
- Config flow with a searchable operator picker (search by name, refine and resubmit) sourced live from ElCom's official LINDAS registry, instead of scrolling through ~600 entries
- Each operator is labeled with a direct-link or auto-detect hint so link-quality issues are visible before setup, not after — the "direct link" hint is backed by a live reachability + content check (not just the URL's shape), since ElCom's self-reported registry is often stale or points at soft-404 pages
- Manual tariff file URL override during setup, for the (common) case where ElCom's registered link for an operator doesn't work at all
- Fully manual rate entry as a further fallback, offered automatically when neither the registered link nor a manual URL resolves: high/low tariff rate, high-tariff time window and weekdays, optional monthly base/grid fee — still gets a current-price sensor and adjustable national levies/VAT
- The operator's ElCom registration is re-checked on every update (not just once at setup): operators re-report their tariff-file link annually, and a stale link that keeps answering with old data would otherwise never be noticed. The stored link is corrected automatically when it changes.
- The actual tariff-file link is freshly re-discovered on every update instead of being cached after the first resolve — so a changed filename behind an operator's page that itself didn't change is picked up too, not just an outright broken link.
- A user-supplied manual URL override is never touched by either of the above — it stays exactly as entered.
- A manual rate entry is re-checked once a day in the background for a newly working operator link, raising a repair notification (Settings → System → Repairs) when found, since municipality/customer tariff still need to be picked by hand before switching over.
- All energy + grid tariff products as `sensor.elcom_<operator>_<product>`, with automatic high/low tariff switching by weekday + time
- Fixed high-tariff / low-tariff reference sensors (`_high` / `_low`) alongside every time-based tariff sensor
- `sensor.elcom_<operator>_tariff_level` — indicator of whether the configured tariff is currently on high or low tariff
- Metering fees and all served municipalities' surcharges as individual sensors
- `sensor.elcom_<operator>_price_current` / `_high` / `_low` — combined price (energy + grid + municipal surcharge + national levies + VAT) for the configured municipality and customer tariff, with a `calculation` attribute spelling out the full calculation
- `number.elcom_<operator>_national_levies` / `number.elcom_<operator>_vat_percent` — national levies and VAT rate, directly adjustable
- Multi-language support (German, English, French, Italian) for entity names, device info, tariff-level labels, and the calculation text
- Multi-instance: one entry per operator/municipality/customer-tariff combination
- Data refreshed every 24 hours
